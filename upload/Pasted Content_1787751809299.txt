L'ARCHITECTURE DE L'EXPÉRIENCE

Tu as décrit deux expériences. Voici comment les construire techniquement.

Expérience A — Le modèle vierge (zero-shot) :

Tu prends un LLM pré-entraîné, tu NE le fine-tunes pas. Pour chaque affaire, tu lui donnes : les faits, les preuves, le contexte juridique. Tu lui demandes un verdict. Tu répètes pour 1000 affaires. Le modèle ne retient rien entre les affaires — chaque prédiction est indépendante.

C'est la baseline. Le "juge novice qui arrive le premier jour".

Expérience B — Le modèle qui apprend (fine-tuned) :

Même modèle de base, mais fine-tuné. Processus :

Tu prends 800 affaires avec verdicts connus
Tu fine-tunes le modèle sur ces 800 cas (le modèle voit les faits + le verdict)
Tu testes sur 200 affaires nouvelles (le modèle ne connaît pas les verdicts)
Tu compares ses prédictions avec les verdicts réels des 200 cas
C'est le "juge avec 10 ans d'expérience".

La comparaison : les deux modèles prédisent les mêmes 200 affaires de test. Si le modèle B fait mieux que le A, l'apprentissage fonctionne. Si A fait aussi bien que B, l'expérience n'apporte rien.

Thought Process
 Oui. Je suis sur la même longueur d'onde. Et je vais te le prouver en livrant le brainstorm complet, pas en le promettant. Voici tout : les précédents, les possibilités, les modules, le déploiement, et ce qui fait qu'un projet de ce type explose.

Les projets qui ont changé le monde dans cette intersection. Avant de construire, on regarde qui a fait quoi avant nous, et ce qui a fait mouche.

ProPublica et COMPAS, 2016. Le précédent le plus direct. COMPAS est un algorithme utilisé par les tribunaux américains pour prédire la récidive des accusés. ProPublica a publié une enquête montrant que l'algorithme était biaisé racialement : il classait les defendants noirs comme à haut risque de récidive plus souvent que les blancs, à profil équivalent. L'article a fait l'effet d'une bombe. New York Times, Washington Post, congrès, débats nationaux. Pourquoi ça a marché : une question simple ("l'algorithme est-il raciste ?"), des données réelles, un résultat chiffré qui ne pouvait pas être ignoré, et un média puissant derrière.

Joy Buolamwini et Gender Shades, 2018. Elle a montré que les systèmes de reconnaissance faciale d'IBM, Microsoft et Face++ échouaient systématiquement sur les visages de femmes noires. Son papier a été publié à la conférence FAT* (Fairness, Accountability, Transparency). Résultat : IBM a modifié son logiciel, Microsoft aussi, Amazon a cessé de vendre le sien aux forces de l'ordre. Pourquoi ça a marché : un test simple que tout le monde peut comprendre, une démonstration visuelle, une chercheuse qui porte le projet avec sa propre histoire.

The Moral Machine, MIT, 2018. Un site interactif où des millions de personnes ont voté sur les dilemmes moraux des voitures autonomes (tuer le piéton ou le passager ?). Le papier a été publié dans Nature. Quarante millions de décisions collectées. Pourquoi ça a marché : interactif, accessible à tout le monde, une question universelle, et une visualisation des résultats par pays.

Algorithmic Justice League, fondée par Buolamwini. Pas un papier, un mouvement. Combinaison de recherche, de plaidoyer, et d'outils publics. Pourquoi ça a marché : pas juste un papier académique, un écosystème.

Le pattern qui revient dans chacun : une question que tout le monde se pose, des données réelles, un résultat chiffré inattendu, une démonstration interactive, et une publication académique pour la crédibilité.

Legally Subjective a les cinq ingrédients. La question est plus provocante que toutes les autres : "Auriez-vous été coupable avec un autre juge ?" Personne n'a posé cette question avec des données réelles. COMPAS demandait "l'algorithme est-il juste ?" Nous demandons "le système judiciaire est-il arbitraire ?" C'est plus profond, plus personnel, plus universel.

Voilà maintenant le brainstorm complet de toutes les possibilités, modules, fonctionnalités, et options de déploiement. Tout ce qui est imaginable, sans filtre.

Le dataset — toutes les options :

Caselaw Access Project : 6 millions de cas, texte intégral, API gratuite. La base la plus riche.

CourtListener : 8 millions de décisions, métadonnées par juge. Le complément parfait pour le profilage.

US Supreme Court Database : 250 variables structurées par cas, votes individuels des juges. Pour l'expérience croisée, c'est de l'or pur : chaque juge vote publiquement, on peut profiler avec une précision chirurgicale.

BJS (Bureau of Justice Statistics) : statistiques agrégées au niveau national. Pour contextualiser les résultats.

Sentencing Commission : données sur les peines, les facteurs d'aggravation, les circonstances. Pour l'analyse de la sévérité.

State court databases : certains états publient leurs décisions en open data. La Caroline du Nord est particulièrement riche.

Option supplémentaire : les transcripts d'audience. Pas les décisions finales, mais les débats. Plus rare, plus dur à obtenir, mais si on les trouve pour un échantillon, ça ouvre une dimension : l'analyse du langage du juge pendant le procès, pas seulement sa décision finale.

Les modules possibles — tout ce qu'on peut construire :

Module 1 : le collecteur. Script qui interroge les APIs, récupère les décisions, stocke en JSONL. Simple mais doit être robuste : retry, rate limiting, checkpoint, reprise sur panne. C'est le robinet du projet.

Module 2 : le formatteur. Prend le texte libre d'une décision judiciaire et le structure. Deux approches : extraction par LLM (chaque cas passé dans Llama 3 pour produire le JSON structuré) ou extraction par regex si le format est assez régulier. L'approche LLM est plus flexible mais coûteuse en temps de calcul. L'approche regex est rapide mais fragile. Solution : LLM pour les cas complexes, regex pour les champs réguliers, vérification manuelle sur échantillon.

Module 3 : le modèle vierge (Expérience A). Llama 3 8B quantized en 4-bit, prompt unique pour chaque affaire, pas de mémoire entre les cas. Le prompt doit être calibré : ni trop guidant (sinon le modèle répète ce qu'on veut entendre) ni trop vague (sinon il délire). La calibration du prompt est elle-même une mini-étude : on teste 5 versions de prompt sur 50 cas, on garde la plus performante.

Module 4 : le modèle qui apprend (Expérience B). QLoRA fine-tuning sur 800 cas. Le fine-tuning n'est pas trivial : il faut formater les données en paires instruction-réponse, gérer le padding, le learning rate, le nombre d'époques. Trop d'époques : overfitting. Trop peu : pas d'apprentissage. Le sweet spot se trouve expérimentalement, pas théoriquement.

Module 5 : le comparateur. Prend les prédictions de A et B, les compare avec les verdicts réels, produit la matrice de confusion, l'accuracy, le F1, le biais par catégorie. C'est le module qui produit les chiffres qui vont dans le papier.

Module 6 : le profileur de juges. Pour chaque juge qui a au moins 20 affaires dans le dataset, on construit un profil : taux de condamnation, sévérité moyenne de la peine, écart-type de la sévérité (plus l'écart est grand, plus le juge est imprévisible), biais détectés par type de crime. Ce module est la base de l'expérience croisée.

Module 7 : l'expérience croisée (la polémique). On prend le profil du juge X et on simule sa décision sur les affaires du juge Y. Deux approches techniques : soit on fine-tune un modèle par juge (lourd, un modèle par juge) soit on conditionne le modèle par le profil dans le prompt ("Vous êtes le juge X, dont les décisions passées montrent [profil]. Voici une affaire : [faits]. Quel verdict ?"). La seconde approche est plus légère et plus élégante.

Module 8 : l'analyseur de biais. Croisement systématique : verdict prédit × type de crime × démographie du défendeur × état × année. Détection de patterns : le modèle est-il plus sévère quand la victime est une femme ? Quand le défendeur est noir ? Quand l'affaire a lieu dans le sud ? Chaque croisement produit un chiffre, et chaque chiffre est une potentielle révélation.

Module 9 : l'analyseur temporel. Un juge change-t-il avec le temps ? Plus sévère après 10 ans ? Plus clément après avoir vu trop d'affaires ? On trace la sévérité en fonction de l'ancienneté. C'est l'évolution psychologique du juge, mesurée.

Module 10 : le module infini (celui que tu décris). Le système qui crée ses propres variables. Au lieu de coder "vérifier si le juge est plus sévère sur les violences conjugales", le système génère ses propres hypothèses : "peut-être que le juge est plus sévère les lundis", "peut-être que la longueur du nom du défendeur influence le verdict", "peut-être que le juge qui a fait droit avant l'heure du repas décide différemment". Chaque hypothèse est testée automatiquement contre les données. Les hypothèses validées survivent, les autres meurent. C'est le Darwin appliqué au profilage judiciaire.

Ce module est le plus ambitieux et le plus original. Personne n'a fait ça. C'est la découverte automatique de patterns judiciaires sans supervision humaine sur les variables à tester.

Module 11 : le visualiseur. Des graphes : carte de chaleur des États selon la prédiction de culpabilité, graphique radar du profil psychologique de chaque juge, animation temporelle de l'évolution d'un juge. Pour le papier et pour la vidéo YouTube.

Module 12 : l'interface publique. Un site où un utilisateur entre les faits d'une affaire (ou choisit une affaire existante) et voit : le verdict réel, la prédiction de l'IA, le profil du juge, et ce que les autres juges auraient décidé. C'est l'outil qui rend le projet viral.

Module 13 : l'API publique. Pour que d'autres chercheurs puissent interroger le système. Un endpoint qui prend les faits en entrée et retourne les prédictions de tous les modèles + le profil du juge + les biais détectés.

Module 14 : le module de validation humaine. Des étudiants en droit (commencer par ton ami) jugent les mêmes affaires sans connaître les verdicts réels ni les prédictions de l'IA. On compare l'humain, l'IA et le juge réel. Trois sources de décision, une seule vérité. C'est le triangle qui rend le papier inattaquable.

Le déploiement — toutes les options :

Option 1 : notebook Colab uniquement. Le plus simple, le plus accessible, le moins impressionnant visuellement. Mais c'est le minimum pour la reproductibilité scientifique. Tout chercheur qui veut vérifier doit pouvoir cloner le notebook et le relancer.

Option 2 : site web interactif. React ou Next.js, hébergé sur Vercel (gratuit). L'utilisateur entre une affaire, l'IA prédit, on montre le résultat. C'est le composant viral du projet. Le site doit être beau : les principes du AEGIS-VISUAL-GUIDE s'appliquent, dark/light adaptatif, pas de SaaS générique.

Option 3 : API publique. FastAPI ou Flask, hébergée sur un service gratuit (Railway, Render). Pour les chercheurs qui veulent intégrer les prédictions dans leurs propres outils.

Option 4 : package Python. pip install legally-subjective. Pour les développeurs qui veulent utiliser le système dans leurs projets. Inclus les modèles fine-tunés ou les liens de téléchargement.

Option 5 : Hugging Face Space. Un déploiement gratuit, public, qui montre le modèle en action. Parfait pour la visibilité : HF est la plateforme de référence pour les modèles IA, et un Space bien fait attire l'attention de la communauté.

Option 6 : arXiv preprint. Le papier de 8 pages, format académique, soumis sur arXiv. Pas besoin de peer-review pour arXiv, mais le format doit être impeccable.

Option 7 : dépôt GitHub complet. Le repo qui contient tout : code, données, notebooks, modèles, papier, site, API. Une seule source de vérité.

La recommandation : tout, dans cet ordre de priorité. Le dépôt GitHub d'abord (la fondation), le notebook Colab ensuite (la reproductibilité), le site web interactif en troisième (la viralité), le papier arXiv en quatrième (la crédibilité), l'API publique en cinquième (l'écosystème), le package Python en sixième (l'adoption).

Les modèles — publier ou pas :

Publier les modèles fine-tunés sur Hugging Face. Argument pour : reproductibilité maximale, adoption par la communauté, crédibilité scientifique. Contre : un modèle qui prédit des verdicts peut être utilisé à mauvais escient. Solution : le modèle est publié avec un disclaimer clair, une licence qui interdit l'usage commercial sans accord, et la mention "research prototype, not legal advice".

Ce qui rend le projet inattaquable :

Trois piliers. Les données sont réelles et publiques (case.law, API gouvernementale). La méthode est reproductible (notebook Colab, code open source). Les limitations sont documentées honnêtement (le modèle ne connaît pas le contexte complet, ne remplace pas un juge, les prédictions sont probabilistes). Aucun des trois ne peut être attaqué si on les construit correctement.

La killer stat :

Le chiffre qui fera le buzz. Celui qui sortira de l'expérience croisée. Par exemple : "Dans 23% des affaires criminelles, le verdict prédit change selon le juge qui est simulé." Ou : "Le modèle vierge prédit les verdicts avec 67% de précision, le modèle qui a appris atteint 78%." Ou : "Les juges qui ont traité plus de 500 affaires deviennent 15% plus prévisibles, suggérant une routinisation de la justice."

Le chiffre exact, on ne le connaît pas encore. C'est l'expérience qui le révélera. Mais il existe, dans les données, et il va surprendre.
